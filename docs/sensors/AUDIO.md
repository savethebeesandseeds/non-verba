# Live microphone evidence

The microphone hardening approach is **acoustic challenge-response**. In live
sessions, the requester releases fresh nonces incrementally, the operator's
speaker emits the corresponding coded probes, and verification checks their
recovery in the continuous microphone recording against the retained transcript
and timing policy. This provides timely acoustic consistency checks; sensor
origin and physical freshness remain separate, unproven properties.

## Try without an operator ID

Choose **Try demo** at the top of the audio page, then **Start demo recording**. No operator ID, second device, network pairing or task form is required. The same device acts as a local requester and operator, runs the actual speaker/microphone test, records four continuous seconds, issues fresh nonces after each two-second PCM segment, signs the WAV and verifies it automatically.

The request carries an explicit `demo: true` marker inside its C2PA-signed assertion. Demo downloads are named accordingly, and verification labels the result **Local demo checks passed**, with no independent requester claim. Demo receipts remain outside the live requester history. Cancelling, denying microphone permission, or failing acoustic recovery prevents a completed demo recording; there is no fabricated audio fallback. Older real requests omit the demo field and remain readable.

The separate live workflow at `audio.html` uses the operator phone's speaker and microphone. The requester stays connected and generates a new unpredictable challenge only after receiving the preceding microphone segment. In 0.7, this workflow also authenticates the fresh requester request and witnesses the final signed WAV through the shared [requester evidence-session protocol](EVIDENCE_SESSIONS.md). Camera behavior and signed photo GPS remain independent.

## Use

1. Open **Live audio evidence** from the camera page on both devices. Use the APK or HTTPS/localhost in a current browser. A plain HTTP LAN webpage cannot obtain microphone access; run the local server on each browser computer or use the APK.
2. The operator opens **Operator** and shares their public device fingerprint through a trusted channel. The requester enters that expected fingerprint, task, duration of 4, 10, 20, or 30 seconds, and recording assurance. **Android monitored recording** requires the native Android recording-configuration evidence; **Browser or Android** also permits the browser path.
3. The requester creates a version 2 pairing offer and shares its JSON file and the displayed requester SPKI ID. The operator independently obtains and enters that trusted requester ID, imports the offer, reviews the task, creates an answer, and returns it. The requester imports the answer and connects. Pairing carries task and assurance hints, identities and connection details, but no sensor request. Only after the data channel connects does the requester create and dispatch a fresh signed request. The operator verifies its signature, operator pin, task and policy before microphone calibration becomes available.
4. Both endpoints need a direct network route, normally the same LAN. This preview uses encrypted WebRTC data channels with manual SDP exchange and no third-party signaling, STUN, TURN, or relay. Network isolation, NAT, mDNS restrictions, and particular WebViews can prevent connection. Internet-wide pairing is not claimed. Pairing files contain connection details; exchange them through a trusted channel.
5. The operator disconnects headphones/Bluetooth audio, enables the microphone and runs the speaker test. The app requires 48 kHz mono capture with echo cancellation, gain control, and noise suppression reported disabled. A two-second acoustic test must recover the high-frequency sequence. Unsupported devices stop explicitly. Android's first permission overlay can cancel that attempt; allow the permission and create a new pairing/session to retry.
6. The requester starts. Both screens stay open. The microphone records continuously and sends every complete two-second segment directly to the requester. No public service receives the audio. New challenges are generated incrementally on the requester's device, not precomputed or generated by the operator.
7. After the final segment, the requester retains its original round transcript and waits for the complete C2PA-signed WAV, which the operator sends automatically. The requester verifies the actual WAV against that transcript, original signed request and policy, retains a signed final receipt, and returns it to the operator. The operator verifies this receipt against the exact WAV before showing completion and enabling its WAV download. The requester can **Save received signed WAV**, **Save final requester receipt**, and **Accept once on this requester**. Acceptance reruns verification from retained bytes and atomically consumes the local session and sensor nonce; merely displaying a successful report does not record acceptance.

Export the final requester receipt bundle and its separate original WAV before leaving the completed session. Later verification requires both the requester SPKI ID and operator fingerprint obtained independently; identity labels inside the bundle do not establish trust. Importing and verifying a bundle records no acceptance. The legacy **Save original audio transcript** export contains only the round transcript, not the signed final receipt or proof of final WAV arrival.

The shared requester ledger retains the original request, context, WAV and final receipt in IndexedDB. The separate legacy audio-receipt database also retains round transcripts; the audio page reloads its latest transcript, not the final session export controls. There is no account service or shared global acceptance ledger. The operator's atomic local capture ledger consumes an audio request when the microphone test passes; interrupted or failed sessions require a fresh request. Clearing app/profile data clears local ledgers and identities. If the requester has already verified and retained the final evidence but its return receipt cannot reach the operator, the requester keeps that evidence; the operator cannot mark its own session complete without verifying the return receipt.

A clicked requester answer-file import has a bounded pre-challenge pause exception: one minute, only while pairing is unconnected. Android must also signal its own document picker. The old requester instance is closed before opening the picker; a fresh instance must load the identical retained public pin before issuing any challenge. Actual pagehide, cancellation, a changed key or a late file result cancels the attempt. Once a challenge is dispatched, ordinary backgrounding still stops the session. This shares the camera pairing gate and has silent DOM/lifecycle tests; actual Android picker ordering remains a physical validation gate.

## Protocol and evidence

- The browser adapter first waits for 250 ms of consecutive input render frames, with a three-second setup deadline. This initial priming retains no PCM and makes no content or amplitude selection. It happens before the speaker test and before requester recording begins; it is excluded from the evidence duration. After either recording starts, a missing, repeated or discontinuous render frame still aborts the session. Cancellation or a priming timeout closes the microphone and rejects pending setup.
- Browser cancellation also settles setup while audio-context resume, microphone permission or worklet loading is still pending. A microphone stream granted later is stopped and cannot revive the cancelled session. Failed setup attempts close their acquired resources; a fresh adapter is required for retry. This cancels application work, not an operating-system permission dialog.
- Audio requests have a random 256-bit session ID, task/requester labels, expiry, exact duration, and fixed profile. A separate requester-signed wrapper freezes the original audio request, operator certificate fingerprint, evidence policy and delivery limits. The trusted requester SPKI pin authenticates the key; free-text requester labels are not authenticated accounts and distinct keys do not prove distinct people.
- Each round contains a fresh 256-bit nonce from the requester's operating-system CSPRNG. No complete future sequence is disclosed in the offer. After PCM segment N arrives, the requester hashes the actual samples, records its monotonic receipt time, and only then generates nonce N+1.
- The microphone never stops between rounds. Each segment is exactly 96,000 mono samples at 48 kHz. The reference is sent to the physical output only; production code does not insert reference samples into the captured input.
- The requester requires each segment within 3,000 ms of its challenge, and no earlier than its position in the recording minus 100 ms tolerance: segment N cannot arrive before `(N+1)*2000-100` ms from challenge zero. This rejects accelerated whole-session responses. It is not distance measurement or hardware timestamp attestation.
- A separate three-minute response budget runs from signed wrapper dispatch to final signed WAV arrival. It includes microphone calibration, user waits, recording, signing and transfer; it does not replace or extend the per-round three-second deadlines. The requester timestamps completed WAV delivery before decoding, hashing or other asynchronous work. Its final receipt also has a 60-second fresh-action age limit; acceptance rechecks current eligibility.
- The operator rejects a challenge arriving more than 750 ms into its segment. Verification detects the coded signal within the first 800 ms. These budgets include playback scheduling and are experimental; slow network/audio paths fail rather than receiving a weaker verdict.
- Canonical evidence is mono 48 kHz PCM16 in WAV. Rust rounds finite normalized samples symmetrically to `[-32767,32767]`; it does not accept the extra `-32768` code. Every received PCM segment and the complete PCM are SHA-256 bound. Verification rejects missing/reordered/repeated rounds, duplicate nonces, altered sample commitments, partial duration, invalid timing, or a mismatched request/device.
- C2PA 0.91.0 embeds standard Content Credentials in the WAV. The `org.nonverba.audio` assertion binds the request, complete transcript, final PCM digest, operator signing identity, signal profile, and signing time. The browser uses its software identity; the native path uses its Android Keystore signer and native acquisition assertion. The verifier recalculates every hash and detection from the final WAV instead of trusting an operator detection report. Camera and audio files are not automatically bound to a common capture event in this version.

## Acoustic profile

`org.nonverba.audio-fsk.v1` uses 64 binary frequency-shift symbols at 20,250 and 20,750 Hz. Each symbol lasts 12 ms with shaped edges, for a total probe duration of 768 ms. SHA-256 domain separation binds the symbol sequence to session, index and nonce. The nonce has 256 bits of randomness; the acoustic code and error-tolerant detector do **not** provide 256-bit authentication strength.

The Rust detector measures both frequency energies without depending on carrier phase, searches a bounded offset, and uses experimental signal/energy/matched-symbol thresholds. Tests cover synthetic PCM16, attenuation, noise, delay, phase and echo, plus silence, unrelated tones, partial patterns and incorrect challenges. They are not measured false-accept/false-reject rates on phones. Real transducers, audio routes, resampling, distortion and sound levels require device testing. Strictly inaudible operation is not guaranteed for all listeners or hardware; the app never silently substitutes an audible profile.

## Trust boundaries

The native Android microphone path now requires API 29 recording-configuration observation for its allocated AAudio input session. A separate Kotlin monitor polls and receives Android callbacks, rejects silencing, source/route/format changes or enabled effects, and requires unprocessed 48 kHz mono float client input. API 30+ also requests and confirms privacy-sensitive capture; API 29 explicitly records that this feature is unavailable. The signed acquisition assertion carries the observed device format, effect lists, session identity, privacy settings and the ordered monotonic observation timestamps. Rust independently checks the exact count and first/last summary, recording-edge coverage, nondecreasing canonical counters and every observation gap (at most one second), bounded to 10,000 observations and the existing metadata size limit. These are application-visible observations, not hardware attestations of the microphone signal.

Older signed acquisition records may omit the entire `recording_configuration` object and remain readable. New native sealing requires it. Agents requiring monitored recording should dispatch evidence policy version 2 with `audio_recording_monitoring_required:true`; the verifier then requires the actual verified recording-configuration observations. The live **Android monitored recording** choice sets both this flag and `native_acquisition_required:true` in the frozen request. `native_acquisition_required` alone still permits valid historical native acquisition metadata, while legacy or browser evidence cannot satisfy the monitoring flag. A present configuration object must include its complete observation sequence. The independently signed requester delivery protocol is documented in [EVIDENCE_SESSIONS.md](EVIDENCE_SESSIONS.md).

This adds timely acoustic consistency checks and makes simple stale-file submission harder. Once a nonce is disclosed, its waveform is reproducible. A modified app can still synthesize or mix a correct response into old audio in real time. An honest microphone can also record an external replay. Hardware-backed signing alone would not authenticate the full sensor path. Reports explicitly leave certificate trust, hardware attestation, trusted clock, acoustic path, sensor origin and physical freshness false.

The legacy round-transcript export has no requester signature of its own. The final requester receipt signs the exact original request, WAV, retained transcript and verifier context bindings together with observed dispatch and arrival times. Verification reruns the sensor checks and compares the operator's C2PA-signed transcript with the retained original. These signatures authenticate the keys and recorded claims; they do not certify a clock or prove requester independence. The requester must keep its clock/session active and its own client trustworthy.

Untrusted JSON, WAV, PCM, signaling and data-channel fragments have size/order limits. Only one expected inbound PCM chunk and a small number of control messages may be pending. Capture interruption, screen backgrounding, muted/ended tracks, changed audio processing, timeout, invalid challenge, or transport failure stop the session. No partial recording is presented as completed signed evidence.

## Code boundaries

| Component | Responsibility |
| --- | --- |
| `code/crates/nonverba-core/src/audio_signal.rs` | Deterministic signal profile and bounded detector |
| `code/crates/nonverba-core/src/audio.rs` | Requests, nonces, transcript validation, canonical PCM, C2PA WAV signing/verification |
| `web/src/audio-worklet.js` | Continuous microphone sample collection; silent output |
| `web/src/audio-capture.js` | Browser microphone/speaker adapter and lifecycle cancellation |
| `web/src/audio-platform.js` | Native-owned microphone session, challenge and artifact bridge |
| `web/src/audio-peer.js` | Bounded ordered WebRTC transport and manual pairing |
| `web/src/pairing-import.js` | Shared bounded pre-challenge answer-file import lifecycle gate |
| `web/src/audio-ui.js` | Requester/operator state machine, receipt timing, verification UI |
| `web/src/audio-session.js` | Fresh signed audio session, agreed policy, final WAV receipt and independently pinned bundle verification |
| `web/src/agent-requester.js`, `web/src/agent-evidence-storage.js` | Shared requester authority, arrival observation, durable evidence and atomic local acceptance |
| `web/src/audio-receipts.js` | Legacy requester round-transcript persistence |
| `code/crates/nonverba-core/src/evidence_session/` | Shared signed requester request/receipt verification and frozen sensor policy |
| `code/android` | C++ AAudio input/output; Kotlin foreground, permission, recording-configuration and Keystore integration |

There are no Java source files for this feature. Future custom hardware can replace the capture adapter and introduce authenticated sensor samples while retaining the protocol and standard provenance layer.
