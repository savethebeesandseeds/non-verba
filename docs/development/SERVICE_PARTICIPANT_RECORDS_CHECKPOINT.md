# Private participant records checkpoint

Completed 21 October 2026. Hero 11's selected local participant-record and explicit
publication scope passed after the completed account/device lifecycle.
Implementation and detailed evidence stay private. Acceptance used synthetic
container-only HTTP clients; Hero 10 owns APK integration.

The selected scope retains synthetic private revisions and audit history. One
confirmed account can keep a separate registration record for each declared
Operator/Requester role. The unchanged shared Rust registration policy validates
optional personal details, accessibility support preferences and self-reported
certifications. No biometric, face-reference or media upload is authorized.

Only deliberately selected display name and organization may enter a published
profile. Other confirmed local accounts may fetch that projection by exact opaque
profile ID. Anonymous access, search, a public catalog and named-task disclosure
remain outside this phase. Counterparty-sharing preferences alone disclose
nothing. No location, work presence or private contact, accessibility, identity
or certification data belongs in the reader projection.

Saving or correcting private details does not publish changes implicitly.
Publication requires an exact current preview and separate deliberate action;
withdrawal hides the current projection while private history and backups remain
retained. Historical operation receipts cannot reactivate a withdrawn profile.
Neither publishing nor withdrawing changes work state, signing authority or
sensor permissions. Actual HTTP preserved the fixture's clocked-out state and
tested recovery while published without changing private/public records or work.
Component tests separately checked publication independence under stored Hold,
clocked-out and signed-out states; these were not new-account work actions.

Distinct versioned synthetic notices cover private retention, unverified
certification declarations and publication. Applicable acknowledgments retain
the exact text, version, digest, actor and revision. The earlier memory-only
inspection acknowledgment is insufficient for server retention. These are
synthetic operating notices, not adopted legal terms or sufficient contractual
notice. Identity/certification verification remains unimplemented and cannot be
claimed through a submitted form.

The versioned API has closed request/result schemas, separate client review and
server revisions, bounded history pages and exact retained record bytes with
encoding provenance. Independent byte/hash checks passed for new shared-JCS
records and preserved earlier exact-JSON records. Historical successful-operation
replay and owner reads left earlier bytes, hashes and receipts unchanged. Encoding
compatibility does not rewrite history or give an old receipt current authority.

Actual HTTP with two confirmed local accounts passed independent Operator and
Requester private streams, exact applicable notices, owner/reader denials,
stale/conflicting retries, and concurrent revision and publication/withdrawal
cases. Default sharing and private correction did not publish; explicit current
preview, notice and deliberate action published only the selected allowlist.
Unknown and withdrawn profiles returned the same hidden response, and historical
publish replay did not reactivate withdrawal. Account recovery while published
preserved private/public/work state and continued to deny old authority.

A full graceful restart of all owned services exercised saved, still-valid
access and refresh credentials before any fresh login; revoked credentials
remained denied. Original-operation replay preserved private revision, notice,
publication and work witnesses. Against the isolated restored service, the saved
access token had expired and was correctly refused with 401. Its saved refresh
credential succeeded, after which all eight historical operations and the
recovery receipt returned unchanged results. Private/public durable witnesses
remained unchanged, and withdrawn-profile lookup stayed unavailable. Fresh
authentication and rate bookkeeping are expected and excluded from that durable
identity comparison.

The isolated restore matched all 38 table witnesses and 22 **current** objects.
All 27 protected authentication/account tables, including the five new participant
tables, preserved application access while denying viewer SELECT and PUBLIC
privileges. Source and recovered HTTP replay of the earlier signed service
scenario passed, together with independent unchanged shared-Rust verification of
restored signed files. That evidence belongs to the earlier synthetic scenario;
the new participant accounts did not form a new Contract or Assignment.

Formatting, all-target Clippy, 16 normal tests and all 13 opt-in PostgreSQL/S3
checks passed, including four participant checks. The bounded privacy audit used
known private/credential markers from captured state and local confirmation
material to check selected current-run logs, journals and nested race reports. It
found none of the checked markers in those captures; it is not an
unrestricted all-secret audit. API and worker targets were returned to the source
database/bucket, and final environment verification passed readiness,
authenticated storage, requested GPU access and all 27 viewer denials.

Synthetic-only remains a declared usage boundary, not an automatic content
classifier. This result selects no real-data retention/erasure policy,
verification authority, central biometric handling, adopted legal terms, external
delivery, anonymous discovery or public deployment. It proves neither physical
sensor shutdown nor production identity/security assurance. Recovery covers an
exported database snapshot and checked current objects, not an atomic database/
object-store cut or historical-version recovery; issuer secrets, runtime
credentials and external systems remain separate. The other proposed service
Goals are unactivated.
