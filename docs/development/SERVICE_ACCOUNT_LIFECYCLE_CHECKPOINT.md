## Initial lifecycle checkpoint — 21 October 2026

Completed 21 October 2026. Hero 11's durable accounts and device sessions Goal
passed its selected local scope after the first bounded service release. Server
source, configuration and detailed evidence remain private. Hero 10 owns all APK
work; this acceptance used container-only synthetic HTTP clients.

The selected initial policy is one account per email, supporting both Operator
and Requester roles. Email comparison trims surrounding whitespace and compares
ASCII case-insensitively; it does not fold provider-specific aliases. Account
and principal identifiers are opaque server-generated values. Contact
confirmation is separate from claimed registration details, identity assurance,
role eligibility, protocol signing authority and sensor consent.

This phase uses synthetic contacts, a private local confirmation outbox and the
existing development OIDC issuer. It creates no real mailbox delivery or external
provider integration. Persisted issuer/subject bindings must not merge accounts
merely because emails match. Optional external linking remains unselected.

Lost-device recovery requires a single-use recovery code and a separate contact
confirmation challenge. It revokes sessions and old signing-key authorization;
replacement signing keys require separate approval. Recovery preserves signed
history and does not restore a lost private key or resume work. Hold and stopped
work state remain independent of login, renewal and joining another device.

The versioned OpenAPI now specifies enrollment, private operation status,
confirmation/recovery receipts, own account and roles, device/session inventories,
key proof and revocation results, and applicable errors. Exact retries return
historical receipts; current inventory remains separate from those receipts.
There is no HTTP key-approval route. Retained legacy seeded principals continue
to use their existing login/device-session paths without implicit enrollment.

Actual local HTTP acceptance passed reviewed minimal enrollment, local contact
confirmation, normalized-email competition and stable/conflicting retries. One
account deliberately added Operator to its initial Requester role. Unbound login
could manage its own confirmed account but could not authorize protocol APIs.
Wrong roles, stale review, incorrect factors and proofs, and foreign resources
were denied. First, additional and replacement device keys each required
possession proof followed by a separate private administrator approval.

Owner-scoped inventories and session/device revocation passed. Hold and clock-out
did not resume through login, refresh, another approved device or recovery.
Recovery rotated login/recovery credentials, revoked old sessions and key
authority, consumed old codes/challenges and invalidated older pending key
requests. An old-generation approval received the expected typed refusal.
Completed recovery retries returned the original receipt; changed recovery input
could not overwrite it. Old key proofs remain cryptographically inspectable
against retained public keys while their current authorization remains revoked.

Two full graceful service restarts preserved saved, still-valid access/refresh
credentials and continued to deny revoked credentials. These checks used the
saved credentials before fresh login. Component tests also passed concurrent
duplicate/revocation cases, deliberately expired or exhausted factors, consumed

work to clocked-out state. Expiry is rechecked after relevant lock waits; no

An isolated restore recovered all 33 table witnesses and 16 current objects with

Formatting, Clippy, normal tests and opt-in managed PostgreSQL/S3 checks passed.

The result establishes a local software state machine, not real mailbox delivery,
